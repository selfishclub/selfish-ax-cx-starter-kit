# cx-sync — 화면이 바뀌면 정책도 같이

## 왜 있나

초안기는 화면을 직접 보지 못해요. `policy/answers.md`에 적힌 문장만 알아요. 화면 · 가격 · 일정 · 로그인 방법을 바꾸면서 문서를 같이 안 고치면 **없는 기능을 안내해요.** 실제로 두 번 났어요 — 로그인 방법을 바꿨는데 정책은 옛 방법을 안내하고, 본인 확인 절차를 없앴는데 정책은 「번호로 연결합니다」. 첫 안내가 틀리면 문의를 줄이는 게 아니라 늘려요.

## 언제 쓰나

- 가격 · 일정 · 환불 기한 · 로그인 방법 · 버튼 위치 · 상품 구성을 바꾼 작업의 **커밋 전에**
- 사용자가 「정책 맞춰 줘」 「점검해 줘」라고 할 때
- 브리핑이 「틀렸을 수 있는 답」을 짚었을 때

## 순서

1. **무엇이 바뀌었나.** 사용자에게 바뀐 것을 묻거나(화면 · 가격 · 일정 · 조건 · 로그인), 코드 저장소가 있으면 `git diff`에서 고객 눈에 보이는 변화만 추린다 — 문구 · 버튼 · 순서 · 조건 · 기한 · 숫자.
2. **정책 문서를 위에서 아래로.** `policy/answers.md`의 문장을 하나씩 1번과 대조한다. 순서는 문서대로: 말투 → 절대 하지 않는 것 → 첫 반응 → 서비스 구조 → 유형별 표준 답 → 확인 필요 경우.
3. **제안을 표로.** 「지금 문장 · 바꿀 문장 · 근거」 세 칸. 12살도 알 수 있게 **왜 바꿔야 하는지**를 먼저. 고칠 게 없으면 없다고 말한다.
4. **승인 뒤에 고친다.** `answers.md`만 고친다. 같은 사실을 다른 파일에 또 적지 않는다. 숫자(기한 · 가격)는 가능하면 문장에 직접 쓰지 않고 「서비스 구조」 표를 가리킨다.
5. **같은 커밋에 넣는다.** 화면 변경과 정책 변경이 따로 다니면 그 사이가 사고 구간이다.
6. **확인.** 바뀐 사실을 건드리는 질문 두세 개를 초안기(또는 Claude)에 실제로 물어보고 답이 새 문장대로 나오는지 본다.

## 하지 않는 것

- 승인 없이 문구를 고치지 않는다. 배포하지 않는다.
- 돈 · 개인정보에 답하게 만드는 방향으로 고치지 않는다.
- 화면에 없는 기능을 「곧 생겨요」라고 적지 않는다. 지금 되는 것만.
